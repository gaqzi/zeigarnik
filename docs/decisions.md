## Accepted

### zg-orj: The domain core is event-sourced in the Decider style, with the session as its only aggregate

Areas: core

#### Context

zg needs each thread's history, a replay of any session, several views of one record (pane, handoff, re-injection, review), and rules testable as given/when/then. Several rules span more than one thread: "children close first", "one open goal", and propagation across threads.

#### Decision

zg stores events, and state is a fold over them. The core is a Decider (Chassaing, "Functional Event Sourcing Decider", https://thinkbeforecoding.com/post/2021/12/17/functional-event-sourcing-decider): `decide(state, command) → events | refusal`, `evolve(state, event) → state`, and an initial state. Views are folds over the events, computed in the same process. There's no CQRS machinery: no separate read stores, buses or asynchronous projections.

The aggregate is the session: one event stream per Claude Code session, so every rule is checked by one `decide` over the whole session state.

#### Rationale

History and replay come for free. Given/when/then tests map onto the rules, any new view is another fold, and logs double as eval fixtures. The Decider is the least machinery that gives all this, and has the shape of Elm's update split in two. Only the session contains every rule, and with a single user a large aggregate costs nothing.

#### Alternatives Considered

- State only (Elm without a log): no history.
- State plus a history list: replay added later; history and state drift apart.
- Full CQRS with event sourcing: eventual consistency and infrastructure for problems a single-user, single-process plugin doesn't have.
- A thread or the goal's tree as the aggregate: rules cross both.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human asked for 'events, replay, and clear views into it' and worried 'CQRS/ES maybe are a bit too big'. They wanted 'events about named domain types and not update field x to y'. Agreed after the comparison of state-based, event sourcing and full CQRS; the human found the Chassaing post. The session aggregate was folded in from a separate proposal after the human asked why it mattered.

### zg-tjz: Events are past-tense domain facts that keep how each decision was reached, both sides verbatim

Areas: core

#### Context

Understanding a session means seeing how each decision was reached, not just the outcome. Agreements are sometimes hedged ("good start, we can change it later"), and the exchange that led there matters. Claude's transcript is local and easily lost; the zg log is committed.

#### Decision

Events name what happened in the domain (`ThreadResolved`, `DecisionMade`, `CriterionAdded`), never field updates or UI changes. A command's events are appended all at once or not at all, in the order `decide` returned them.

Each thread's history keeps both sides verbatim: `ThreadReplied{thread, author: human | claude, text}`, where Claude's text is the part of its reply addressing that thread. A decision records the human's words of agreement, hedges included. The transcript is referenced by message ID, not copied.

#### Rationale

The log reads as the story of the session, and partial or reordered writes would break replay. The understanding is in the exchange, and the log is committed and costs no context tokens, so keeping both sides is cheap.

#### Alternatives Considered

- Field updates (`SetThreadState`): lose the meaning.
- Only the outcomes, or only the human's words: lose what was agreed to and how firmly.
- A one-line summary of what Claude proposed: loses the details agreed to.
- Copying the whole transcript: tool output and prose that belongs to no thread.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human: 'the events are about the domain and not about the UI'. First agreed to keep raw chat out of the log, then revised: 'sometimes you agree to something quite complex/bad just because you were tired and went yeah, yeah, we can change it later but it's a good start, and seeing that was what the agreement/decision came from is crucial'. Then: 'ThreadReplied also need to contain what the agent said, since a lot of stuff is bounced off each other.'

### zg-su8: A command that would break a rule is refused with the reason and a fix; zg never surprises the human

Areas: core, mod

#### Context

The human can only trust the structure if it never changes behind their back.

#### Decision

A command that would break a rule is refused. The refusal says why, suggests a fix, and goes back to whoever sent it: a tool error for Claude, a notice for the human. zg never does anything automatically that would break a rule, and never surprises the human. Learning what counts as a surprise is zg-u9s.

#### Rationale

Refusing keeps the structure valid; the suggested fix makes a refusal something to act on rather than a dead end.

#### Alternatives Considered

- Accept and flag: leaves the structure invalid.
- Fix it automatically (e.g. cancel open children): surprises the human.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human's words: 'rejects it and says why and suggest how to resolve it, but never do anything automatically that would violate rules and never surprise the human. figuring out what surprises are is a big piece of the feedback zg will have to try and figure out.'

### zg-vgk: Refusals are not events; they go to a separate trace that evals read

Areas: core, storage

#### Context

A refused command changes nothing, but refusals show where Claude and the human misread the structure.

#### Decision

Refusals are not events. Each is recorded as `CommandRefused{command, reason, fix}` in a separate trace that views ignore and evals read.

#### Rationale

A refusal isn't a fact about the session, so it stays out of every view; kept separately, it's raw data for evals and for learning what surprises the human.

#### Alternatives Considered

- Refusals as events: clutter every view.
- Not recording them: lose that data.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human asked 'would we want to record failed events or just successful events? ... we only really care about those that completed fully? And that they're then emitted in the order required'. Agreed: 'ok'.

### zg-2x6: Sinks are instructions, not integrations; the default sink is the handoff

Areas: core, mod

#### Context

Captured items go to whatever tracking the human uses: beads, Jira, files on disk. Claude already knows how to use those through its tools, skills and CLAUDE.md.

#### Decision

zg contains no integration code. A sink is a plain-language instruction for the project ("issues and lasting decisions go to bd as beads"). At close, zg builds the capture list; Claude files each item with its own tools and reports the external reference back through a zg tool, which records it (rule: exports keep their reference). #### Rationale

#### Alternatives Considered

- An adapter per tracker: code to build and maintain for each.
- Command templates (the README's original `sink` option): code-like configuration, limited to what the template covers.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. Replaced a proposal that 'no sink' be special. The human: 'there should always be a default sink that is output. importantly, I don't imagine the sinks are pieces that needs to exist in the plugin as code, I imagine that's where the agent just knows how to interact.'

### zg-r1g: Each session's events are a JSONL file in .zg/sessions/, committed to the repo

Areas: storage

#### Context

The log must survive /clear, resume and restart, be reviewable, and work in cloud sessions whose containers are temporary.

#### Decision

Each session's events are written to `.zg/sessions/<session-id>.jsonl` in the repo, and the file is committed. `$.fs` has no append, so the file is rewritten on every change.

### zg-zo2: After compaction or resume, zg re-injects a short view of the log; the full view is shown on request

Areas: mod

#### Context

Compaction drops the conversation's history from Claude's context, and with it the structure zg is tracking.

#### Decision

After a compaction or a resume, zg re-injects a short view of the log: from slice 1 the goal and open actions, growing with threads, criteria and decisions, always within the re-injection budget. On request (a command, or just asking), zg renders the full view from the log into the conversation.

#### Rationale

A goal that vanishes at the first compaction makes zg unusable. Re-injection is just another fold over the events, so it's cheap to build early and improve later.

#### Alternatives Considered

- Waiting until threads exist: the walking skeleton isn't usable on its own.
- A full dump of the log every time: breaks the budget.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human: 'I'm okay with looking at compaction early, but not if it's a big or complex area ... maybe it's important to do it early and verify it and improve on the format later?' Agreed to minimal re-injection in slice 1, adding: 'also allow the user to ask it to redisplay everything from the log if needed'.

### zg-egt: Evals assert on the event log, 5 runs per case; guardrails must pass every time, behaviours ratchet up from a baseline

Areas: evals

#### Context

Model behaviour (thread grain, propagation, recaps, goal checks, steering) can't be unit-tested, and the model isn't deterministic.

#### Decision

Evals run with `claude plugin eval`. They're scored mostly by deterministic assertions on the event log, with an LLM grader only for what can't be checked mechanically (is the recap any good). Each case runs 5 times. Guardrails (no rule broken, nothing done without the human's confirmation) must pass every time. Behaviours start at the first measured baseline and the bar only ratchets up; slice 4 closes at 80% or better. The no-plugin baseline arm measures what zg adds.

#### Rationale

Deterministic checks are cheap and stable, repeated runs absorb nondeterminism, and ratcheting from a measured baseline beats guessing a bar.

#### Alternatives Considered

- LLM-graded transcripts only: noisy and expensive.
- Fixed bars set upfront: guesses.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. Proposed by Claude at the human's request ('suggest, I'm not good enough at this to steer the conversation but I'll have opinions with options'). Hedged agreement: 'I don't really understand this, but sounds fair enough', then 'sounds good'. Worth revisiting once there are real evals.

### zg-564: Evals cost tokens, so they never run by default; script/test [unit|wiring|eval|all] picks the layers

Areas: tooling

#### Context

Evals call the real model: they take minutes, cost tokens and vary between runs. The repo follows scripts to rule them all.

#### Decision

`script/test` never runs evals unless asked. `script/test unit|wiring|eval` runs one layer; `script/test all` runs every layer, cheapest and fastest first, stopping at the first gate that fails. `script/test` runs `script/fmt` first unless `CI` is set; on CI it checks formatting instead. #### Rationale

One entry point for testing; evals are run on big changes and before closing a slice, not on every edit. Formatting on every local test run keeps the code consistent.

#### Alternatives Considered

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. ### zg-nti: Context loads by area label and by file path, index first

Areas: project

#### Context

Agents should load only the decisions and guidance their work needs, not everything.

#### Decision

Every work bead and decision carries at least one area label, for the areas its work is about: what it changes or builds on. Reading files to understand something, or updating another area to match (a feature that updates the README), doesn't add a label. The areas and their directories:

| Area | Directories |
|---|---|
| core | src/core/ (commands, events, decide/evolve, views as pure functions) |
| mod | src/mod/ (hooks, tools, pane drawing, injection) |
| storage | src/storage/ (log and trace) |
| evals | evals/ |
| tooling | script/, config files |
| docs | docs/, README.md |
| project | .beads/PRIME.md, CLAUDE.md, .claude/rules/ |

`mod`, `storage` and `evals` include `core`. `script/context <id> [--claim]` prints the bead in full, its epic's design, its dependencies, an index (bead ID and title) of the accepted decisions for its areas, and the path rules that apply; full rationale via `bd show <id>`.

Path-scoped rules in `.claude/rules/` load by file: one per area, starting with a line telling the agent to add the area label and rerun `script/context` if the bead lacks it, when its work changes or builds on that area, plus practical how-to for that directory, never restating decisions. `script/decisions` refuses to render while any decision lacks a valid area label, since such a decision never reaches the index; `script/context` warns about unknown area labels on the bead it prints.

#### Rationale

Labels look ahead and load decisions at claim; path rules react to what's actually touched, so drift into another area is caught as it happens. Titles carry the constraint, so the index alone is usually enough.

#### Alternatives Considered

- Loading every decision upfront.
- Always loading core: tooling, docs and project work don't need it.
- Labelling by every directory touched, checked against changed files: labels a feature bead as docs for updating the README, and can't tell whose changes are in a shared working tree.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human proposed it: 'we should also tag work with the area label and then pull in dynamically only the decisions relevant to the core and that area. Maybe testing is another thing to load dynamically.' On path rules: 'love using the path rules like that'. Expects script/context to 'provide all relevant info for the bead'; asked for --claim. Questioned always loading core, leading to the include rule.

Narrowed on 2026-10-22 while building it (zg-bam.9), after the changed-files check flagged incidental edits. The human: 'the lacking the area is only relevant when they're modifying or depending on the area, it's not relevant if they're looking something up out of curiosity or to understand something historical, so we don't want each bead to be labeled with each area just because something is read.' And: 'if the current bead is about changing a feature it shouldn't tag that bead as docs just because it's updating the docs to mention the feature. This seems too broad'. Agreed to drop the changed-files check.
Then moved the label checks out of script/test, after the agent noted that only a decision's labels fail silently. The human, on whether the check pulls its weight: 'those checks aren't useful on CI, only outside CI. I still don't fully understand if the check is that helpful/useful'. On checking in script/decisions and script/context instead: 'I like those changes to decisions/context'.

### zg-pvk: Long-term design decisions are bd decision beads, made together with the human

Areas: project

#### Context

Decisions are made while designing, which today happens in chat. Only some constrain future work; others matter for one bead or one session.

#### Decision

A decision bead records a lasting constraint. The test: would an agent working on a different bead, months from now, go wrong without knowing this? Yes: a decision bead. Only this bead: its design field. Only this session: the handoff. Only the human makes decisions; agents propose and never record one unasked.

- Title: states the constraint so it can be read alone; it's what gets loaded.
- Description: Context, Decision, Rationale, Alternatives Considered. Rules and other decisions are referred to by name or bead ID, never by number.
- Notes: how it was decided, in the human's own words, hedges included.
- Labels: one or more area labels.
- Status: open means still to decide (it can block work); closed with "accepted" means in force; replaced with `bd supersede`.
- `bd compact` and `bd prune` are never run on decisions.
- `script/decisions` renders all decisions into `docs/decisions.md`, which is committed, so the file is always produced the same way.

#### Rationale

Keeping only lasting constraints keeps what's loaded small and trustworthy. bd gives status, blocking, supersedes links and label queries. The rendered file shows decision changes in PR diffs and works when bd is down.

#### Alternatives Considered

- Markdown ADRs (as the beads project does): no status, blocking or links.
- Recording every decision: the set becomes noise and stops being read.
- The beads plugin's convention, open = active: pending decisions wouldn't behave like work.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human: 'I quite like using bd for these things since there is more tooling.' 'no decisions are made here without the humans involvement. be fastidious about the area labels and that what we keep are long-term constraints.' Corrected the context: 'decisions happen while designing and right now we design in chat.' Kept script/decisions 'as a way of being consistent about how to create the file'.

### zg-7zf: Claude interprets the conversation; zg's code only records and enforces

Areas: core, mod

#### Context

### zg-8ex: Events grow without breaking: old logs always replay, a changed event gets a frozen version, and every event change needs the human's sign-off

Areas: core, storage

#### Context

Session logs are committed and kept: they are history, and they double as eval
fixtures. Event shapes will change as zg grows, and every log already written
must still replay.

#### Decision

Events grow without breaking. Any event zg has ever written can be read and
replayed.

- An event's shape only gains fields; existing fields keep their meaning.
- An event that needs a significant change but keeps its name gets a
  `version` field. An event without one is version 0. Once a version is in
  use it is frozen: it only gains fields.
- `evolve` handles every version of every event. Old logs are never rewritten.
- Every new or changed event needs the human's sign-off, as decisions do.
  When designing events, propose them; the human approves before they are
  written.

#### Rationale

Grow, don't break: old logs keep replaying without migrations. Versioning a
changed event, instead of stretching one shape with ever more optional fields,
stops cruft from building up. Events are the record of every session, so
changing them is as lasting as a decision and needs the human.

#### Alternatives Considered

- Migrating old logs in place: rewrites committed history.
- A new event name for every change: loses the domain's own words.
- Only ever adding optional fields: cruft accrues in one shape.

#### How it was decided

Agreed in chat on 2026-10-22, while restructuring docs before slice 0 (zg-bam.9), after the agent proposed keeping committed logs readable. The human: 'we need to be able to handle historical events and if we change events we need to be forward compatible, if events needs to be significantly changed but keep the name then introduce a version field. if the version field is unset it's version 0, if version gets set then freeze it to that version and allow additions. the grow don't break paradigm + versioning to ensure we can handle old things. Overall, we aim to not break things, but we version instead of letting cruft accrue. Event changes also need a human in the loop, same as these decisions.'

### zg-n27: zg's context budget: 3k fixed (cap 5k), checked by a test that counts what zg registers; a small per-turn index, 2k for re-injection; meter thresholds are configurable

Areas: evals, mod

#### Context

The point of zg is short sessions: most should end around 100k tokens, and
none above 200k. zg's code runs in the Claude Code process and costs no
tokens; only what reaches the model does.

zg-o17 had the fixed part measured with `claude plugin details`. Slice 0
(zg-bam.1) found that can't work: `details` reports only what a plugin
declares in files, and zg registers its tools at run time from its hooks
module, so it reports ~0. `$.session.usage({ breakdown: 'full' })` lists zg's
tools at 0 tokens too.

#### Decision

| Part | Budget |
|---|---|
| Fixed: tool schemas and standing instructions | 3k, hard cap 5k |
| Per-turn index of open items | 300 + ~15 per open item |
| Re-injection after compaction | 2k |

A wiring test checks the fixed part (`src/mod/budget.test.ts`): it starts a
session, collects what zg puts in front of the model (the tools it registers
undeferred, and its standing instructions once there are any), and counts
about four characters a token. Rarely used tools are deferred, and details
arrive on request (zg_show). A context meter suggests closing at nudge_at
(default 100k) and presses at push_at (default 150k); both are configurable.

#### Rationale

3k is about 3% of a typical session. 1k can't hold the tool schemas; 10k
spends 10% before any conversation. Thresholds will need to change with use.
Counting what zg registers is the only measure that sees runtime-registered
tools, and it runs with the free tests, so a change that grows the context
fails before it reaches anyone. Four characters a token is an estimate, close
enough for a budget with a hard cap well above it.

#### Alternatives Considered

- A 1k or 10k fixed budget: too tight, or too much of the session.
- Hardcoded meter thresholds.
- `claude plugin details`: can't see tools registered at run time.
- `$.session.usage({ breakdown: 'full' })` in a live session: costs tokens,
  and counts zg's tools as 0.

#### How it was decided

Agreed in chat on 2026-10-22, closing slice 0 (zg-bam.1), after it found claude plugin details can't see runtime-registered tools. The human: 'sure, put that in, if I understand it correct we're at 31 tokens which is significantly less than 3k then by default when loaded right now? (and I guess it'll grow a bit as we then add functionality?)'. The budget itself is unchanged from zg-o17.

### zg-51d: Code work: the main session coordinates; subagents write the tests (red), write the code (green) and review

Areas: project

#### Context

Writing tests and code in the main session fills its context with file dumps and test runs, and pulls it away from the design and the conversation with the human. A review written by the code's author is anchored on it.

#### Decision

For code work, the main session coordinates and doesn't write code or tests itself. It hands each step to a subagent with a narrow brief, at a model that fits the task:
- Red: the test-writer agent (sonnet) loads /workflow:test-design and writes failing tests for the behaviour and rules named in the brief. The main session checks they fail for the right reason.
- Green: the implementer agent (sonnet, or haiku for mechanical changes) makes those tests pass without changing them.
- Review: the reviewer agent (opus) reads the whole change without the main session's conclusions. The main session sorts its findings into what is worth taking and what isn't, with why, and the human decides.
The agents are defined in .claude/agents/, with their models in the frontmatter.

#### Rationale

The main context stays small and on coordination; each piece of work runs narrow and with fresh context; a review not anchored on the author finds more (slice 1's review found an untested pure function and a fallback that recorded an outcome the human never agreed to).

#### Alternatives Considered

- The main session writes tests and code: its context fills with detail, and it reviews its own work.
- One subagent does red, green and review together: it grades its own work, and the main session sees only the end result.
- Choosing the model per task each time: drifts; pinning it in the agent definitions makes it part of the setup.

#### How it was decided

Agreed in chat on 2026-10-22, closing slice 1 (zg-bam.2). The human: 'when it comes to code I want this main session to drive the work but hand off creating tests (to ensure red), writing code (to go green), and then review the whole thing to subagents. I want to use the model that's reasonable for the task at hand (haiku, sonnet, opus). The final review you should review in turn and suggest what is worth taking in and not ... The whole goal is to try and keep the test/code pieces outside of the main loop and really narrow, and to then keep us focused on coordinating.' Then, on the drafted wording and model split: 'the workflow decision sounds good'.

### zg-tjb: Every event that decides or ends something keeps the human's words verbatim as its reason, with their source

Areas: core

#### Context

Understanding a session later means seeing why the human decided or ended
something, in their words (zg-tjz). The close dialog showed the gap: a pick
from options Claude wrote was logged as `picked: <label>`, repeating the
event type, and the human's note was copied into both agreement and reason.
Picks will also come from the pane, and decisions on threads will arrive the
same ways.

#### Decision

Every event that records a decision or an end (a goal, action or thread
closing; a decision made) keeps the human's words verbatim as its `reason`
when they gave any, and `source`, where the words came from: `chat`,
`dialog`, later `pane`. One field for the words, whatever the channel.

Options Claude wrote add nothing of their own: the outcome picked is the
event's type, the label is not recorded, and a note on a pick is the reason.
A bare pick records the source alone.

Every outcome may carry words, success included: the human is never
constrained. Where a rule needs a why (a failed goal), it is checked on the
presence of a reason.

#### Rationale

The words are what explain the decision, so they appear once, unedited, in
the same place on every such event. The type already says what was decided.
The source tells a reader how much context surrounds the words: a dialog note
is all there was, chat words have the conversation around them.

#### Alternatives Considered

- Recording the picked label (`picked: <label>`): repeats the type, and the
  note appeared twice.
- Two fields, a quote for the words and a reason for the why: the same words
  land twice, or Claude edits the sentence to split them.
- A dialog raised by zg's own code via `$.ui.ask`: deterministic and
  wiring-testable, but the API returns only a label or free text, so the
  human's note is lost.

#### How it was decided

Agreed in chat on 2026-10-22, defining zg-bam.14 after zg-bam.11's manual check. The human: 'I want the option that is the types that we have decided on to be set as the type of decision, and then the reason'; 'in most cases it's covered by the event type so it's not really helpful. in those cases, we only really care about the reason given (if any)'; 'it doesn't hurt to have a reason for successes either ... don't constrain the human if they want it'; on a separate quote and reason: 'if we end up having two fields for a very similar thing, then I'd rather have one field and a type, or source (source: picker|chat, for example)'; on the name: 'I prefer reason over quote ... because reason is why we ended up with this event'. Still version 0: 'we haven't even shipped this thing'. Scope: 'keep it open to let the user express themselves as much as possible', dialog and pane alike. Open until the human accepts it.

### zg-o17: zg's context budget: 3k fixed (cap 5k), a small per-turn index, 2k for re-injection; meter thresholds are configurable

Areas: evals, mod  
Closed: superseded by zg-n27

#### Context

The point of zg is short sessions: most should end around 100k tokens, and none above 200k. zg's code runs in the Claude Code process and costs no tokens; only what reaches the model does.

#### Decision

| Part | Budget |
|---|---|
| Fixed: tool schemas and standing instructions | 3k, hard cap 5k |
| Per-turn index of open items | 300 + ~15 per open item |
| Re-injection after compaction | 2k |

Tests check these (`claude plugin details` reports the fixed part). Rarely used tools are deferred and details arrive on request (`zg_show`). A context meter suggests closing at `nudge_at` (default 100k) and presses at `push_at` (default 150k); both are configurable.

#### Rationale

3k is about 3% of a typical session. 1k can't hold the tool schemas; 10k spends 10% before any conversation. Thresholds will need to change with use.

#### Alternatives Considered

- A 1k or 10k fixed budget: too tight, or too much of the session.
- Hardcoded meter thresholds.

#### How it was decided

Agreed in chat on 2026-10-22, while designing before slice 0. The human: 'I'd love it if most sessions end around 100k tokens and ideally no more than 200k. smaller is better.' Asked 'what's a good number for that budget? 1k? 5k? 10K?' and agreed to 3k/5k. On the meter: 'we probably have to make it configurable in the future. so better not hardcode it'.
